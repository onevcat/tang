## 1. 项目目标

用 Go 从零写一个 Tangled 的 CLI 客户端，命名为 `tang`，对标 `gh` 的使用习惯。

**Hard goals (P0–P3)**：
- 用户可以在 git repo 内做完整的 issue / pr 工作流：`tang issue list/create/view/close/reopen/comment`、`tang pr list/view/create/checkout/merge/diff/comment`
- 完整的 auth 与 ssh-key 管理：`tang auth login/logout/refresh/token`、`tang ssh-key add/list/delete`
- repo 元信息：`tang repo view/list/create/clone`
- `tang status`（auth + repo + 服务健康一站式状态）、`tang config`、`tang browse`、`tang completion`
- 单二进制分发；`tang --help` 体验对标 gh

**Capability boundaries（必须真实，不制造 gh 的虚假能力）**：
- `pr create` 以 Tangled 的 patch model 为核心：branch-based / fork-based PR 需要先向 Knot 生成 format-patch，再把 gzip patch 作为 PDS blob 写进 `sh.tangled.repo.pull.rounds[]`
- `pr checkout` 只保证 branch-based / fork-based PR；patch-only PR 没有可 checkout 的 source branch，应给清晰错误
- `pr merge` 当前不支持 gh 的 `--squash|--rebase|--merge` strategy 语义；Tangled 的 `sh.tangled.repo.merge` 只接收 patch + target branch + commit metadata
- issue/pr 的 state/status record 在协议中存在，但当前 AppView 是否消费这些 records 需要 P2/P3 实测；CLI 可以做到自洽，不能预先承诺 Web UI 一定同步

**Architectural commitment（P0–P3 必须做对，不是 future work）**：
- **PDS / Knot / AppView / Constellation 四块组件全部可配置**，除默认配置值、测试数据和文档示例外，源码中**不硬编码任何一块的 host**
- **PDS 通过 DID document 动态解析**，绝不假设默认 PDS（不要继承 TS 版 `bsky.social` 的硬编码 bug）
- 默认体验对齐**通过 tangled.org 注册的"原生用户"**（PDS = `tngl.sh`、Knot = `tangled.org`、Constellation = `microcosm.blue`），开箱即用
- 用户使用**自建 PDS / 自建 knot / 第三方 constellation** 的能力是**第一优先级设计目标**——意味着接口、配置、文档全部要 design-for-extension，不是事后再补
- 详见 §4.4 与 §5.2

**Non-goals (本次不做)**：
- `tang api` 通用透传子命令（理由见 §5 决策记录）
- release / gist / codespace / gpg-key / ruleset / project 等 Tangled 协议没有的功能
- `tang knot/spindle/star/follow/profile` 等 Tangled 特色命令（留给 P5+）
- Web UI、TUI（之后再说）
- Windows 上的 keychain 体验深度打磨（先能跑就行）

### 4.3 包之间的边界

- **`internal/cli/`**：只编排，不写业务逻辑。每个命令的 RunE 函数：解析 flag → 调 `internal/auth` 取 session → 调 `internal/tangled/*` → 把结果丢给 `internal/output`。
- **`internal/tangled/`**：所有 PDS / Knot XRPC 调用都集中在这里，业务函数对外暴露纯 Go struct（不要让 `core/api/tangled.RepoIssue` 泄漏到 cli 层）。这层是未来切换 SDK 的隔离屏障。
  - **PDS client**：登录、refresh、`createRecord` / `putRecord` / `deleteRecord` / `getRecord` / `listRecords` / `uploadBlob`，host 来自 `session.PDS`，auth 是用户 access JWT。
  - **Knot client**：`sh.tangled.repo.create` / `compare` / `diff` / `merge` / `mergeCheck` 等 git-related endpoint，host 来自 repo record 或 `knot.hosts` 解析。
  - **Service auth**：Knot 写操作必须先向 PDS 调 `com.atproto.server.getServiceAuth(aud=did:web:<knot>, lxm=<method>)`，再用返回 token 访问 Knot；不能把普通 PDS access JWT 直接打到 Knot。
- **`internal/atproto/`**：唯一做 handle/DID/PDS 解析的地方。任何代码想知道"这个 handle 的 PDS 在哪"必须走这里，**禁止硬编码 PDS host**。
- **`internal/auth/`**：唯一接触 keychain 的地方。Session struct 必须含 PDS URL（来自 `internal/atproto` 解析）。
- **`internal/git/` `internal/repo/`**：唯一接触 `git` shell 的地方。Knot 识别走配置的 `knot.hosts` 列表，不硬编码。
- **`internal/constellation/`**：URL 来自 `internal/config`，不硬编码 microcosm.blue。
- 测试时通过 interface 做 mock：`internal/tangled` 暴露 `IssueAPI interface { List(...) ... }`，`internal/cli` 注入。

### 4.4 去中心化模型（Tangled 默认 + 横向扩展）

Tangled 不是单一服务，是 **4 块解耦组件**的组合。tang 必须把每一块当作可换的依赖：

| 组件 | 作用 | tang 对它的态度 | 默认值 | 配置入口 |
|---|---|---|---|---|
| **PDS** | 用户 record 存储 + 认证 | **从 DID document 动态解析**，绝不假设 | 由 handle 解析得出 | `--pds <url>` flag / `TANG_PDS_URL` env（兜底） |
| **Knot** | git 数据 + git-related XRPC | 配置 `knot.hosts` 白名单匹配 git remote URL | `["tangled.org"]` | `tang config set knot.hosts ...` |
| **AppView** | web UI 展示（CLI 几乎不用） | 仅用于 `browse` 命令跳转 | `https://tangled.org` | `tang config set appview.url ...` |
| **Constellation** | 跨 PDS 反向链接索引 | 配置项可换 | `https://constellation.microcosm.blue` | `tang config set constellation.url ...` / `TANG_CONSTELLATION_URL` env |

**两个核心心智模型**：

1. **PDS-agnostic**：tangled.org 注册的用户 PDS 实际是 `tngl.sh`（不是 `bsky.social`）；bsky.app 注册的用户 PDS 是 `bsky.social`；自建 PDS 用户 PDS 是各自域名。tang **从 handle 自动解析 PDS**，对这三类用户行为完全一致。**实现层禁止任何 fallback 到具体 host 的逻辑**——解析失败就明确报错。

2. **Tangled.org ≠ Tangled 协议**：tangled.org 是协议的一个实现 + 公共服务；用户可以自建 PDS、自建 knot、用别的 constellation，仍然完整使用 Tangled 协议。tang 的设计要让"自建 X" 的用户感觉到这是 first-class scenario，不是 hacky workaround。

**典型的多组件组合**（都要支持）：

| 用户类型 | PDS | Knot | Constellation |
|---|---|---|---|
| tangled.org 原生注册（默认） | `tngl.sh` | `tangled.org` | `microcosm.blue` |
| Bluesky 用户用 Tangled | `bsky.social` | `tangled.org` | `microcosm.blue` |
| 自建 PDS + 用 tangled.org knot | 自建 | `tangled.org` | `microcosm.blue` |
| 完全自建 | 自建 | 自建 | 自建 / `microcosm.blue` |

| D15 | Knot 写操作必须使用 service-auth token，不复用 PDS access JWT | core 的 Knot `repo.create` / `repo.merge` 等写 endpoint 受 `VerifyServiceAuth` 保护 |

### 5.1 为什么不做 `tang api`

`gh api` 的价值前提是 GitHub REST/GraphQL API 有**版本承诺与文档**。Tangled 当前情况：

- 协议处于 v0.0.x，lexicon 仍可能 break（虽然主名字空间相对稳）
- `sh.tangled.repo.temp.*` 系列是**显式标注 temp 的**，明确不稳定
- 没有公开的"API stability"政策声明
- core 已经预生成了 Tangled lexicon wrapper，P0-P3 的能力不需要给用户暴露 raw call

**结论**：不做 `tang api`。如果将来 Tangled 给出 stable API 承诺，再补也不迟。本次省下的精力放到 pr/repo 命令的打磨上。

### 5.2 PDS / Knot / Constellation 的具体配置面

每个去中心化组件的配置入口（在 §4.4 表格基础上展开）：

**PDS** — 默认**不需要任何配置**：
- `tang auth login` 时输入 handle → 自动通过 `internal/atproto.ResolveHandle` 解析 → 拿到该 handle 的 PDS URL
- session 保存在 keychain 时**带上 PDS URL**，后续所有 XRPC 调用都用这个 URL
- 例外：`--pds <url>` flag 或 `TANG_PDS_URL` env 可覆盖（用于测试 / DID document 异常的边缘场景）
- **绝不实现"如果解析失败用 bsky.social"这类 fallback**

**Knot** — 配置文件 `~/.config/tang/config.toml`：
```toml
[knot]
hosts = ["tangled.org"]  # 默认；用户加自建：tang config set knot.hosts tangled.org,knot.example.com
```
- git remote URL 的 host 在 `knot.hosts` 中即被识别为 Tangled remote
- 解析逻辑在 `internal/git/remote.go`，Phase 1 task 8

**Constellation** — 同样在 `~/.config/tang/config.toml`：
```toml
[constellation]
url = "https://constellation.microcosm.blue"  # 默认
```
- env 覆盖：`TANG_CONSTELLATION_URL`
- 命令行：`--constellation-url <url>`（极少用）

**AppView** —— tang 几乎不直接调，只在 `browse` 跳转时用：
```toml
[appview]
url = "https://tangled.org"
```

**完整默认配置**（`~/.config/tang/config.toml` 不存在时的隐式值）：
```toml
[knot]
hosts = ["tangled.org"]

[constellation]
url = "https://constellation.microcosm.blue"

[appview]
url = "https://tangled.org"

# 注意：没有 [pds] 段。PDS 永远来自 DID document 解析。
```

### 5.3 gh 对齐原则

尽量保留 `gh` 的命令形状，但只在 Tangled 有真实能力时对齐：

| gh shape | tang 处理 |
|---|---|
| 全局 `-R, --repo [HOST/]OWNER/REPO` | 保留；HOST 对应 AppView/Knot host 时解析为 Tangled repo |
| `issue/pr list/view/create/comment/close/reopen` | 保留 |
| `issue/pr view --web` | 保留；内部调用 `browse` |
| `pr create --base --head --fill` | 保留；实现为 Tangled branch compare → format-patch → blob → pull record |
| `pr checkout` | 保留；仅 branch/fork-based PR 支持，patch-only PR 明确 unsupported |
| `pr merge --squash/--rebase/--merge` | 不保留；当前 Tangled merge endpoint 不支持 strategy |
| `auth status` | 保留为 `tang status --section auth` alias |
| release / gist / project / codespace 等 | 不实现；Tangled 当前无对应协议能力 |

1. **`internal/config/store.go`** —— 配置层（先做，后续模块依赖它）

### Phase 3 — Repo + PR (~1–2 晚)

**目标**：覆盖 repo 元信息和 Tangled 当前能力可支撑的 PR 工作流。PR 是本项目最重要且风险最高的阶段：必须按 Tangled 的 patch/rounds/blob 模型实现，不能照搬 GitHub 的 branch-native PR 心智模型。

**任务**：

1. **`internal/tangled/repos.go`**：
   - `GetRepo(ctx, owner, name) (*Repo, error)` — 读 `sh.tangled.repo` record
   - `ListRepos(ctx, owner) ([]Repo, error)` — listRecords for `sh.tangled.repo`
   - `CreateRepo(ctx, session, name, opts) (*Repo, error)` — 两阶段：
     1. PDS `getServiceAuth(lxm=sh.tangled.repo.create, aud=did:web:<knot>)`
     2. Knot `sh.tangled.repo.create` 创建 git repo / mint `repoDid`
     3. PDS `putRecord` 写 `sh.tangled.repo`，字段包含 `name`、`knot`、`repoDid`、`description`、`createdAt`
     4. PDS 写入失败时尽力调用 Knot `sh.tangled.repo.delete` 清理 orphan repo
2. **`internal/cli/repo.go`** 子命令：
   - `tang repo view [<owner>/<name>]` — 当前目录 default
   - `tang repo list [<owner>]` — 默认列当前用户的
   - `tang repo create <name> [--description D] [--knot HOST] [--default-branch BRANCH]`
   - `tang repo clone <owner>/<name> [<dir>]` — resolve handle→DID→clone URL，`exec.Command("git", "clone", url, dir)`
3. **`internal/tangled/pulls.go`**：
   - `ListPulls(ctx, repo, opts) ([]Pull, error)` — constellation 同 issue
   - `GetPull(ctx, repo, identifier) (*Pull, error)`
   - `CreatePull(ctx, session, repo, opts) (*Pull, error)` — branch-based first：
     1. Resolve target repo record：需要 repo AT-URI、repo DID（若存在）、knot host、base branch
     2. 调 Knot `sh.tangled.repo.compare(repo=<repo identifier>, rev1=<base>, rev2=<head>)` 生成 format-patch
     3. gzip format-patch，调 PDS `com.atproto.repo.uploadBlob`
     4. PDS `putRecord` 写 `sh.tangled.repo.pull`，record 必须包含 `target`、`source`、`rounds[0].patchBlob`、`title`、`body`、`createdAt`
     5. `--fill` 可从 format-patch 第一封邮件提取 title/body；没有 `--fill` 时要求 title
   - `SetPullStatus(ctx, session, pullUri, status)` — 写 `sh.tangled.repo.pull.status` record；**必须实测 AppView 是否消费**
   - `ListPullComments(ctx, pullUri)` / `AddPullComment(...)` — `sh.tangled.repo.pull.comment`
   - `FetchPullPatch(ctx, pull, round)` — resolve pull author DID → PDS → `com.atproto.sync.getBlob` 拉取 `round.patchBlob` → gunzip 得到 format-patch
   - `MergeCheck(ctx, pull) (*MergeStatus, error)` — 取 PR 最新 round 的 patch，调 Knot `sh.tangled.repo.mergeCheck`
   - `Merge(ctx, session, pull) error` — 取 PR 最新 round 或 stack 的 combined patch，调 Knot `sh.tangled.repo.merge`；不支持 strategy 参数
   - `GetDiff(ctx, pull) (string, error)` — 对 PR 展示应优先输出 pull record 的最新 patch；`sh.tangled.repo.diff` 是 repo ref diff，不是 PR diff
   - `Checkout(ctx, pull)` — 仅当 `pull.source.branch` 存在时支持；patch-only PR 返回 unsupported
4. **`internal/cli/pr.go`** 子命令：
   - `tang pr list [--state open|closed|merged|all] [--json [fields]]`
   - `tang pr view <n>` — 含 description + comments + 当前 merge status
   - `tang pr create [--title T --body B --base BRANCH --head BRANCH --fill]`
   - `tang pr close <n>` / `reopen <n>`
   - `tang pr checkout <n>` — 解析 PR 的 source branch + remote → `git fetch && git checkout`；patch-only PR 报 unsupported
   - `tang pr merge <n> [--subject S] [--body B]`；**不提供** `--squash|--rebase|--merge`

   - `tang pr view <n> --web` / `tang issue view <n> --web` — gh 对齐 alias，内部走 `browse`
5. 复用 §Phase 2 的 body input、序号解析、output 模块

## 7. 编码约定

- **格式化**：`gofmt` + `goimports`，CI 强制
- **命名**：包名小写单词；导出函数 PascalCase；error 类型 `ErrXxx`
- **错误处理**：
  - 用 `errors.Is/As`，不 string-match
  - cli 层把内部 error 翻译成人类可读（前缀 `✗ `，写到 stderr）
  - `--json` 模式下 error 也输出 JSON：`{"error": "...", "code": "..."}`
- **context.Context**：所有可能涉及 IO 的函数第一个参数 `ctx context.Context`
- **没有全局 var/单例**：依赖通过参数注入（auth client、http client 都是）
- **测试文件命名**：`xxx_test.go` 与源码同目录
- **不要写无意义注释**：函数命名足以解释 what；只在 why 不显然时加注释

### 7.1 与 TS 版本的命名对齐

为了减少切换成本，命令名、flag 名、JSON 字段名都和现有 TS `tang` 保持一致。需要参考时看：

```
/Users/onevcat/Sync/github/tangled-cli/src/commands/*.ts
```

关键 JSON 字段集合（TS 版 `IssueData`）：`number, title, body, state, author, createdAt, uri, cid` —— Go 版完全照搬。

## 8. 测试策略

### 8.1 分层

- **Unit**（同目录 `*_test.go`）：纯函数 / 业务逻辑

### 8.2 必须有的测试用例（P1-P3）

- git remote parsing：fetch=tangled / fetch=github push=tangled / 多个 tangled remote
- session 过期边界（提前 5min refresh）

### 11.6 Tangled 注册用户的真实数据流（参考心智模型）

新用户从 tangled.org 注册：
1. tangled.org 的 appview signup 流程调用配置的 PDS（默认 `https://tngl.sh`）的 `com.atproto.server.createAccount`（见 `tangled-core/appview/signup/signup.go`）
2. 用户得到 handle `<username>.tngl.sh` + DID `did:plc:...`
3. 用户的 records（issue / PR / comment / ssh-key / profile / star / follow / 未来 Bluesky 帖子等）**全部存在 `tngl.sh` 这个 PDS 上**

用户用 tang 时：
1. `tang auth login` → 输入 `<username>.tngl.sh`（或 custom domain handle）
2. tang 调 `core/idresolver` 解析 handle → DID document → 拿到 `service` 字段（`https://tngl.sh`）
3. 调 `tngl.sh` 的 `com.atproto.server.createSession` 登录
4. 后续所有 `createRecord` / `getRecord` 都打到 `tngl.sh`

如果用户后来自建 PDS 并迁移：
1. 通过 atproto 标准 migration 流程把数据从 `tngl.sh` 搬到自建 PDS（`com.atproto.server.activateAccount` 等）
2. DID document 的 `service` 字段更新指向新 PDS
3. **tang 代码无需任何改动**——下次 login 时 `internal/atproto.ResolveHandle` 拿到新 PDS URL 自动连过去

如果用户用自建 knot：
1. `tang config set knot.hosts tangled.org,my-knot.example.com`
2. `git@my-knot.example.com:onev.cat/Prowl` 这种 remote 立即被识别

这种 "**改配置不改代码**" 的扩展能力是 §1 Architectural commitment 的核心交付物。
